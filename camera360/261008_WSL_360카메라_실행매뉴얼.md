# WSL에서 360 카메라 스트림 돌리기 — 따라하기

작성 2026-10-08.

`stream_to_server.py`(360 카메라 → 데이터 스트림)를 윈도우 cmd가 아니라 **WSL 터미널 안에서** 돌리는 절차다.
`server_stream_multi_source.py`(데이터 스트림)도 같은 WSL에서 돌린다. 그러면 360 사진은 WSL 안의 `127.0.0.1:10001`로 바로 들어가서, 윈도우 ↔ WSL 포워딩을 거치지 않는다.

- **코드는 고치지 않는다.** 두 파일 모두 원본 그대로 쓴다.
- 명령은 전부 **WSL(우분투) 터미널**에서 친다. 윈도우 cmd에서 칠 것은 3-3 하나뿐이다.
- 아래 경로 `~/physical_demo/data_stream` 은 **예시**다. 0단계에서 확인한 실제 경로로 바꿔서 친다.

## 2. 파이썬 환경 (venv)

`stream_to_server.py` 에 필요한 것은 `opencv`(FFmpeg 포함)와 `requests` 둘뿐이다.
윈도우에서 쓰던 `venv360\Scripts\activate` 는 윈도우용이라 WSL에서는 못 쓴다.

### 2-1. 이미 있는 data_stream venv로 되는지 먼저 본다

비전(`vision_infer.py`)용 venv에는 opencv와 requests가 이미 들어 있을 가능성이 크다. 들어 있으면 **아무것도 깔지 않고** 그대로 쓴다.

```bash
source venv/bin/activate
python -c "import cv2, requests; print('cv2', cv2.__version__); print([l.strip() for l in cv2.getBuildInformation().splitlines() if 'FFMPEG:' in l])"
```

| 나온 결과 | 판단 |
|---|---|
| `cv2 4.x` (또는 `5.x`) 다음 줄에 `['FFMPEG:   …   YES']` | **이 venv를 쓴다.** 2-2는 건너뛴다 |
| `ModuleNotFoundError` / `ImportError` / `FFMPEG: NO` | `deactivate` 후 2-2 |
| `venv/bin/activate: No such file or directory` | venv가 다른 곳에 있다. 지금 스트림 파일을 켤 때 쓰는 venv로 다시 해 보거나 2-2 |

⚠ 이 venv에 `pip install opencv-python-headless` 를 **하지 않는다.** opencv가 이미 있는 venv에 하나를 더 깔면 둘이 부딪혀 `import cv2` 가 깨질 수 있고, 비전 쪽도 같이 망가진다.

### 2-2. 안 되면 — 360 전용 venv를 따로 만든다 (인터넷 필요)

```bash
deactivate 2>/dev/null
sudo apt update
sudo apt install -y python3-venv
python3 -m venv ~/venv360
source ~/venv360/bin/activate
pip install requests opencv-python-headless
python -c "import cv2, requests; print('cv2', cv2.__version__); print([l.strip() for l in cv2.getBuildInformation().splitlines() if 'FFMPEG:' in l])"
```

- 마지막 줄에서 `FFMPEG: … YES` 가 나오면 된다.
- venv를 data_stream 폴더 **밖**(`~/venv360`)에 만드는 이유: 저장소(git) 안에 만들면 venv 파일 수천 개가 새 파일로 잡힌다(`.gitignore` 는 `venv/` 만 빼 준다).
- `headless` 판 = 화면 띄우는 기능만 뺀 판. 영상 받기(FFmpeg)는 그대로 들어 있다.

### 2-3. 앞으로 "360 venv 켜기"는

| 2-1에서 됐으면 | `source venv/bin/activate` |
|---|---|
| 2-2로 만들었으면 | `source ~/venv360/bin/activate` |

아래에서 **〈360 venv 켜기〉** 라고 쓴 곳에 이 줄을 친다.

## 3. WSL에서 카메라가 닿는지

### 3-1. 카메라 켜기 (`261001 카메라 최종정리2.txt` 1번과 같다)

카메라 전원 → 송신기 켜고 15초 대기 → 수신기(Farsight) 파란불 대기 → 수신기와 노트북을 랜선으로 연결.

### 3-2. WSL에서 확인

```bash
ping -c 2 192.168.100.124
timeout 3 bash -c '</dev/tcp/192.168.100.124/20000' && echo "카메라 20000 OK"
```

- `카메라 20000 OK` 가 나오면 4단계로 간다. 판단은 이 줄로 한다. ping이 안 돼도 이 줄이 되면 괜찮다.
- WSL에서 `ip addr` 를 보면 `192.168.100.x` 가 없을 수 있다(WSL 기본 방식이 NAT라서). **정상이다.** WSL이 바깥으로 나가는 연결은 윈도우를 거쳐서 나간다.

### 3-3. 안 되면 — 윈도우 cmd에서 같은 것을 본다

```
ping -n 2 192.168.100.124
```

| 윈도우 | WSL | 원인 쪽 |
|---|---|---|
| 안 됨 | 안 됨 | 카메라·수신기·랜선 (3-1 순서 다시, 카메라 화면의 IP 확인) |
| 됨 | 안 됨 | WSL 쪽 — 8장 「윈도우에선 되는데 WSL에서만 안 됨」 |

카메라 화면의 IP가 `192.168.100.124` 가 아니면, 아래 모든 `stream_to_server.py` 명령 끝에 `--ip <그 IP>` 를 붙인다.

## 4. 업로드 없이 시험 (`--dry-run`)

**먼저 윈도우 쪽에서 `stream_to_server.py` · `preview_probe.py` 창이 떠 있으면 Ctrl+C로 끝낸다.** 카메라 제어 세션은 하나뿐이다.

```bash
cd ~/physical_demo/data_stream
〈360 venv 켜기〉
python 360camera_work/stream_to_server.py --dry-run --count 20
```

이렇게 나오면 성공이다(숫자는 다르다).

```
======================================================================
stream_to_server — 카메라 192.168.100.124 → http://<server-ip>:7866/upload_pano
  + 같은 사진을 따로 보낼 곳 → http://<server-ip>:10001/upload_pano
  목표 5.0 fps | JPEG q92 | capture_id=LIVE_STREAM  (고정)  [DRY-RUN]
======================================================================
[연결] Fingerprint=…
[프리뷰] rtmp://192.168.100.124:1935/live/preview  (3840x1920, 10240 kbps)
[스트림] 열림 3.38s
  #1    나이    28ms  인코딩   54ms  업로드     0ms  | PC구간    82ms   332KB  dry
  …
  #20   …                                                         dry
======================================================================
종료 — …초 동안 20장 업로드 (… fps 실측)
```

- 맨 위에 서버 주소(`<server-ip>`)가 찍혀도 `[DRY-RUN]` 이면 **실제로 보내지 않는다.** `--upload` 를 안 줘서 기본 주소가 찍힐 뿐이다.
- 줄 끝이 전부 `dry`, `업로드 0ms` 면 카메라 → WSL 구간이 된 것이다.
- `인코딩` 값을 봐 둔다. 5단계 `--fps` 의 주기(3장/초면 333ms)보다 넉넉히 작아야 그 fps가 나온다.

## 5. 실제 실행 — 터미널 3개

계속 떠 있어야 하는 프로그램이 셋이라 터미널을 나눈다. **터미널 1 → (2) → 3 순서로 켠다.** 360(터미널 3)을 먼저 켜면 받을 곳이 없어서 줄마다 `ERR` 가 찍힌다. 멈추지는 않고, 터미널 1이 뜨면 그때부터 들어간다.

### 터미널 1 — 데이터 스트림 (지금 하던 그대로)

```bash
cd ~/physical_demo/data_stream
source venv/bin/activate
redis-cli -p 6380 ping
```

`PONG` 이 아니면 Redis부터 띄운다. 지금 쓰던 명령이 있으면 그것을 쓴다. 같은 노트북 안에서만 읽으면 아래 한 줄로 충분하다.

```bash
redis-server --port 6380 --save "" --appendonly no --daemonize yes
redis-cli -p 6380 ping
```

- `vision_infer.py` 맨 위 주석의 명령처럼 테일넷 주소(`100.x`)에도 묶는 명령은, 그 주소가 없는 현장(테일넷 안 붙음)에서는 Redis가 시작하지 못할 수 있다.

```bash
python server_stream_multi_source.py
```

- 옵션(`--on …`, `--robot1 <IP>` …)은 **지금 쓰던 것 그대로** 붙인다. 360만 시험하려면 `--on cam360`.
- 시작 화면에 `cam360 :10001  영상 ← stream_to_server.py …` 줄이 있어야 한다(`--on` 으로 cam360을 뺐으면 360이 안 들어간다).

### 터미널 2 — 실시간 비전 (쓸 때만, 지금 하던 그대로)

```bash
cd ~/physical_demo/data_stream
source venv/bin/activate
python vision/vision_infer.py
```

### 터미널 3 — 360 카메라

```bash
cd ~/physical_demo/data_stream
〈360 venv 켜기〉
python 360camera_work/stream_to_server.py --fps 3 --upload http://127.0.0.1:10001/upload_pano
```

**`--upload http://127.0.0.1:10001/upload_pano` 는 반드시 붙인다.**
- 빼면 기본값인 서버(`<server-ip>`)로 보낸다. 인터넷 없는 현장에서는 장마다 최대 15초씩 멈춘다.
- 주소만 적고 `--upload` 를 빼면(`… --fps 3 http://127.0.0.1:10001/upload_pano`) `unrecognized arguments` 오류로 시작도 안 된다. `최종정리2.txt` 106행이 이렇게 적혀 있으니 그 줄을 그대로 복사하지 않는다.

필요하면 붙이는 것:

| 상황 | 붙일 것 |
|---|---|
| 카메라 IP가 다름 | `--ip <카메라 IP>` |
| fps 바꾸기 | `--fps <숫자>` (4단계의 `인코딩` 값을 보고 정한다) |
| 측정용으로 N장만 | `--count <N>` (N장 보내고 통계를 찍고 끝남) |
| 인터넷이 될 때 유니티 경로(서버 7866)에도 같이 | `--upload http://127.0.0.1:10001/upload_pano --upload http://<server-ip>:7866/upload_pano` — **엣지(127.0.0.1)를 첫 번째로** 적는다. 첫 번째 주소만 응답을 기다리므로, 서버를 첫 번째에 두면 망이 흔들릴 때 전체가 느려진다 |

## 6. 잘 들어오는지 확인

**터미널 3** — 이런 줄이 계속 찍힌다.

```
  #12   나이   40ms  인코딩   60ms  업로드    4ms  | PC구간  104ms   900KB  saved
```

줄 끝이 `saved` 면 데이터 스트림이 받아서 저장한 것이다.

**터미널 1** — 처음에 한 번, 그 뒤 10초마다:

```
cam360 영상 받는 중 — /upload_pano 로 127.0.0.1 에서 올라옴
…
받은 양
  cam360 영상   3.0장/초 (누적 …)
```

**아무 WSL 터미널에서** (선택):

```bash
curl -s http://127.0.0.1:10001/health
```

`"frames"` 숫자가 늘고, `"status"` 에 `받는 중 (/upload_pano ← 127.0.0.1)` 이 보이면 된다.

저장된 것(data_stream 폴더에서):

```bash
ls stream_data/cam360/                                   # 실행 시각(YYYYMMDD_HHMMSS) 이름의 폴더들
tail -1 stream_data/cam360/<가장 최근 폴더>/frames.jsonl
redis-cli -p 6380 xlen camera_stream:cam360
```

`frames.jsonl` 한 줄의 `sender` 안에 `capture_id` · `camera_id` · `seq` · `timestamp` 가 있으면 윈도우에서 보낼 때와 같은 모양이다.

🔄 **v2 판(2026-10-14 뒤):** `sender` 안이 `capture_id` · `camera_id`(`cam360-001_main`) + 공통 머리(`schema_version` · `source_id` · `node_id` ·
`zone_id` · `session_id`) · `sequence_id`(정수) · `timestamp`(ISO, `+09:00`) · `encoding` · `width` · `height` 다 — 옛 `seq` 는 없다. 기록 칸도
`stream` · `frame_file` · `received_by` · `received_at` 으로 바뀐다(옛 `source` · `file` · `host`).

## 7. 끝내기

창을 그냥 닫지 말고 **Ctrl+C** 로 끝낸다. 순서는 켠 것의 역순이다.

1. 터미널 3 (360) `Ctrl+C` — 카메라 프리뷰를 끄고 통계를 찍는다. 창을 닫아 버리면 프리뷰가 켜진 채로 남을 수 있다.
2. 터미널 2 (비전) `Ctrl+C`
3. 터미널 1 (데이터 스트림) `Ctrl+C` — 소스별 합계를 찍는다.
4. 카메라 · 송수신기 전원.
5. `stream_data/` 폴더를 백업한다.

## 8. 안 될 때

| 증상 | 원인 | 조치 |
|---|---|---|
| `[연결] 시도 1 실패: … port=20000 …` (`timed out` · `No route to host` · `Connection refused`) 가 3번 나오고 끝남 | WSL에서 카메라가 안 닿음 | 3단계 |
| `[연결] 시도 N: … already connected by another` | 다른 창(윈도우 쪽 `stream_to_server` · `preview_probe`, 또는 앞서 띄운 것)이 카메라 세션을 쥐고 있음 | 그 창을 Ctrl+C로 끝내고 다시 |
| `[스트림] 열기 실패: rtmp://…` | 카메라 프리뷰는 켜졌는데 영상을 못 엶 | 2-1의 확인 줄에서 `FFMPEG: YES` 인지 다시 본다. 맞으면 송수신기 연결 상태를 본다 |
| `[스트림] 5초 동안 새 프레임이 없습니다 — 다시 붙습니다` | 무선(Farsight) 구간이 끊김 | 스스로 다시 붙는다(`[재연결] 스트림 다시 열림`). 계속 반복되면 송수신기 거리·전원 |
| 줄 끝이 `ERR:HTTPConnectionPool(host='127.0.0.1', por…` | 데이터 스트림(터미널 1)이 안 떴거나, `--on` 에서 cam360을 뺐음 | 터미널 1 확인, `curl -s http://127.0.0.1:10001/health` |
